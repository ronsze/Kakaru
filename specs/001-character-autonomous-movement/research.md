# 리서치: 캐릭터 자율 이동

스펙의 요구를 Electron(TypeScript)으로 구현하기 위해 정해야 할 항목과 결정을 기록한다.
모든 NEEDS CLARIFICATION은 아래에서 해소했다. 단, "검증 필요" 표시는 실제 기기에서 확인해야
하는 가정이다(quickstart.md의 검증 절차 참조).

## R1. 창 구성: 디스플레이마다 오버레이 창 1개

- **결정**: 연결된 디스플레이마다 투명·테두리 없는·항상 위 `BrowserWindow`를 하나씩 만들고,
  각 창은 해당 디스플레이의 전체 영역(`bounds`)을 덮는다. 캐릭터는 가상 데스크탑 좌표에서
  하나만 존재하며, 현재 위치가 속한 디스플레이의 창에서만 그린다.
- **근거**: 여러 모니터에 걸친 단일 거대 창은 OS별 배율(DPI)·Spaces/가상 데스크탑 처리가
  불안정하다. 디스플레이별 창은 배율 차이를 창 단위로 격리하고, 모니터 연결·해제 이벤트에
  창을 추가·제거하는 것으로 FR-008을 처리할 수 있다.
- **대안**: 모든 모니터를 덮는 단일 창(배율·OS 동작 차이로 기각), 캐릭터 크기의 작은 창을
  이동(전체 화면에서 제한 없이 움직이고 추후 3D·이펙트를 넣는 방향과 맞지 않아 기각).

## R2. 클릭 통과: 메인 프로세스 커서 폴링

- **결정**: 오버레이 창은 기본적으로 `setIgnoreMouseEvents(true)`(전부 통과) 상태로 두고, 메인
  프로세스가 `screen.getCursorScreenPoint()`를 약 60Hz로 폴링해 커서가 캐릭터 히트 영역
  안에 있을 때만 해당 창의 통과를 해제(`false`)한다. 히트 영역은 캐릭터 스프라이트의 외접
  원/사각형으로 시작한다. 롱프레스 드래그 중에는 통과를 해제한 상태를 유지한다.
- **근거**: `setIgnoreMouseEvents(true, { forward: true })`는 mac/Windows에서 마우스 이동을
  전달해 주지만, 전달된 이벤트에 의존하면 OS별 동작 차이가 생긴다. 폴링은 두 OS에서 동일한
  코드이며 비용도 작다(헌장 원칙 III, FR-005, FR-007).
- **대안**: `forward: true` + 렌더러 히트 테스트(OS별 편차로 기각), 픽셀 단위 알파 히트 테스트
  (현재 스펙에 불필요, YAGNI로 기각 — 3D 도입 시 재검토).
- **검증 필요**: 폴링 주기에서 캐릭터 진입 시 첫 클릭이 유실되지 않는지(진입 후 1프레임 지연).

## R3. 전체 화면 앱 위 표시

- **결정**: macOS는 `setAlwaysOnTop(true, 'screen-saver')`와
  `setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true })`, Windows는
  `setAlwaysOnTop(true, 'screen-saver')`를 사용한다. 이 설정은 OS별 어댑터
  (`PlatformAdapter`) 뒤에 둔다.
- **근거**: 엣지 케이스 "전체 화면 앱 실행 중에도 방해하지 않는다"를 만족하려면 통과 상태의
  오버레이가 전체 화면 앱 위에 있어도 입력을 가로채지 않아야 한다.
- **한계**: 독점(exclusive) 전체 화면 게임 위에는 표시되지 않을 수 있다. 이는 허용하며
  스펙의 "방해하지 않는다"는 만족한다(보이지 않을 뿐 입력은 가로채지 않음). **검증 필요**.

## R4. 이동 가능 영역: 디스플레이 전체 영역의 합집합

- **결정**: 이동 가능 영역은 각 디스플레이의 `bounds`(작업 표시줄·메뉴 막대·Dock 포함)의
  합집합이다. 캐릭터는 이 합집합 밖으로 나가지 않는다. 목표 지점은 합집합 안에서 고르고,
  현재 위치에서 목표까지의 직선이 합집합 안에 있을 때만 채택한다(비직사각형 배치에서 빈 공간으로
  빠지는 것을 방지). 직선 경로가 막히면 다른 목표를 다시 고른다.
- **근거**: "전체 화면에서 제한 없이" 움직이라는 결정과 FR-004, FR-008. 오버레이가 작업
  표시줄 위에 그려지므로 가려지거나 접근 불가 상태가 되지 않는다.
- **스펙 영향**: FR-004의 "사용 가능한 화면 영역"을 "화면 전체"로 해석한다. 문구 정리는
  후속 `/speckit-clarify` 후보.

## R5. 상태와 이동 루프: 메인 프로세스 단일 시뮬레이션

- **결정**: 캐릭터 상태(위치·방향·행동)는 메인 프로세스가 단일 출처로 갖는다. 고정 틱(60Hz)으로
  시뮬레이션하고, 위치를 해당 디스플레이 렌더러에 IPC로 전달한다. 렌더러는 Canvas 2D로
  스프라이트를 그린다. 행동은 `Walking` / `Idle` / `UserControlled` 상태 머신이다.
- **근거**: 오버레이 창이 여러 개여도 캐릭터는 하나이므로 상태를 한 곳에 둬야 한다. 이동
  로직은 Electron에 의존하지 않는 순수 TypeScript로 분리해 단위 테스트가 가능하다(원칙 V).
- **대안**: 렌더러별 시뮬레이션(동기화 문제로 기각).

## R6. 행동 파라미터 기본값 (FR-003, SC-001/002/004)

- 걷기 속도: 80px/s (DIP). 이동 구간: 2~6초. 정지(Idle): 1~4초. 둘 다 균등 무작위.
- 시작: 실행 후 5초 안에 이동 시작(SC-001). 같은 방향 연속 방지: 새 목표는 직전 이동
  방향과 다른 방향 쪽을 우선 선택.
- 사용자 조작(롱프레스·메뉴) 시작 후 0.5초 안에 자율 이동 정지(SC-004): 틱 단위(≈16ms) 반영.
- 값은 `shared/config`에 상수로 두고 사용자 설정 기능은 만들지 않는다(스펙 범위 밖).

## R7. 모니터 변경·절전 복귀 (FR-008, 엣지 케이스)

- **결정**: `screen`의 `display-added` / `display-removed` / `display-metrics-changed`와
  `powerMonitor`의 `resume`을 구독해, 오버레이 창을 재구성하고 이동 가능 영역을 갱신한다.
  캐릭터 위치가 영역 밖이면 가장 가까운 영역 내부 지점으로 옮긴다. 절전 복귀 시 틱 기준 시각을
  초기화해 큰 시간 점프를 방지한다.

## R8. 테스트 전략

- **단위**: Vitest. 이동 로직(상태 전이, 경계 처리, 목표 선택, 영역 합집합 판정)은 순수
  함수로 테스트한다.
- **통합/E2E**: Playwright의 Electron 지원으로 앱 기동·창 생성·IPC 위치 갱신을 확인한다.
- **수동**: 클릭 통과, 전체 화면 앱 위 표시, 멀티 모니터는 자동화가 어려워 quickstart.md의 수동
  절차로 mac/Windows 모두 확인한다.

## R9. 성능 목표 (원칙 III에 따른 수치)

헌장은 수치 기준을 스펙에서 정의하도록 하지만 현재 스펙에는 없다. plan에서는 아래를 목표로
제안하고, 후속 스펙 보완 항목으로 올린다.
- 유휴 상태 평균 CPU 10% 이하(캐릭터 1개, 60Hz 틱 포함), 메모리 300MB 이하. 초기 제안은 3%였으나
  전체 화면 투명 오버레이의 합성 비용 때문에 macOS 실측(약 14%)과 맞지 않아 10%로 완화했다.
- 렌더링 30fps 이상, 가능하면 60fps.

## R11. 캐릭터 디자인: 코드로 그리는 폴리곤 (2D)

- **결정**: 렌더링은 2D로 하고, 캐릭터는 이미지 파일 없이 Canvas 2D의 폴리곤(다각형) 경로로
  코드에서 직접 그린다. 디자인은 AI가 제작하는 임시 디자인이다. 걷기는 다리·몸 폴리곤의 좌표를
  시간에 따라 흔드는 절차적 애니메이션, 정지는 숨쉬기(몸 상하 미세 흔들림) 정도로 한다.
  `heading`에 따라 좌우 반전한다.
- **근거**: 에셋 제작·라이선스 문제 없이 바로 동작을 확인할 수 있고, 최종 에셋(스프라이트
  시트 등)이 정해지면 `src/renderer/draw.ts`만 교체하면 된다(이동 로직·IPC 불변).
- **대안**: PNG 스프라이트 시트(에셋 확정 전이라 보류), 3D 모델(3D 도입 시점에 재검토).
- **범위**: 롱프레스로 집힌 모습과 메뉴 반응 모습은 해당 기능에서 추가한다.

## R10. 빌드 도구

- **결정**: Electron + TypeScript + electron-vite(Vite 기반, main/preload/renderer 3분할),
  패키지 매니저는 npm. 배포 패키징(electron-builder 등)은 이번 기능 범위 밖.
- **근거**: 구성 파일이 적고 TypeScript 3분할을 기본 지원한다(원칙 IV).
