# 리서치: 우클릭 메뉴와 캐릭터 리소스 설정

스펙을 구현하기 위해 정해야 할 항목과 결정을 기록한다. "검증 필요"는 실제 기기에서 확인해야 하는
가정이며 quickstart.md에 절차가 있다. 이 기능은 001의 코드(오버레이 창, `MovementEngine`의
`setUserControlled`, 히트 테스트)를 그대로 이어서 쓴다.

## R1. 메뉴 형태: OS 네이티브 팝업 메뉴

- **결정**: 우클릭 메뉴는 Electron의 `Menu.popup()`으로 띄우는 OS 네이티브 메뉴다. 항목은 이번에는
  "캐릭터 설정" 하나다. 이후 기능은 이 메뉴 정의에 항목을 추가한다.
- **근거**: 화면 가장자리에서 잘리지 않게 위치를 보정하고(FR-005), 메뉴 밖 클릭·Esc로 닫히고(FR-004),
  동시에 하나만 열리는 동작을 OS가 보장한다. 직접 그리는 메뉴 창을 만들 필요가 없어 가장 단순하다
  (헌장 원칙 IV). 사용자 요청의 "메뉴 화면"은 스펙 Assumptions의 "작은 목록"으로 해석했다.
- **대안**: HTML로 그린 커스텀 메뉴 창(디자인 자유도는 높지만 위치 보정·닫힘 처리·접근성을 직접
  만들어야 해서 기각). 메뉴를 꾸미는 요구가 생기면 그때 재검토한다.
- **검증 필요**: 최상위 레벨(`screen-saver`)의 오버레이 위와 전체 화면 앱 위에서도 네이티브 메뉴가
  보이는지(macOS), 메뉴가 열린 동안 오버레이의 클릭 통과 전환과 충돌하지 않는지.

## R2. 우클릭 감지: 오버레이 웹 콘텐츠의 `context-menu` 이벤트

- **결정**: 오버레이 창의 `webContents`에서 `context-menu` 이벤트를 받아 메뉴를 연다. 오버레이는
  커서가 캐릭터 히트 영역 위일 때만 입력을 받으므로(001 R2), 캐릭터가 없는 영역의 우클릭은 이벤트가
  발생하지 않고 아래 창으로 전달된다(FR-002). 렌더러와 preload 변경이 필요 없다.
- **근거**: 001에서 만든 "캐릭터 위에서만 입력 수신" 구조를 그대로 쓴다.
- **한계**: 히트 영역은 반지름 40px 원이므로 이미지의 투명한 모서리를 우클릭해도 열릴 수 있다.
- **검증 필요**: `focusable: false` 창에서 macOS·Windows 모두 `context-menu`가 발생하는지.
  발생하지 않으면 렌더러에서 `contextmenu` DOM 이벤트를 받아 IPC로 알리는 방식으로 바꾼다.
- **스파이크 결과(macOS, 2026-10-22)**: `focusable: false` 오버레이 창 2개(디스플레이 2대) 모두에서
  `webContents.sendInputEvent`로 보낸 우클릭이 `context-menu` 이벤트를 발생시켰다(좌표 전달 확인).
  실제 마우스 우클릭과 Windows는 수동 검증이 필요하다.

## R3. 메뉴 열림 동안의 이동 정지

- **결정**: 메뉴를 열 때 시뮬레이션의 `setUserControlled(true)`, `Menu.popup`의 `callback`(메뉴가
  닫힘)에서 `setUserControlled(false)`를 호출한다. 이미 있는 `MovementEngine` 상태 전이를 쓴다.
  메뉴가 열려 있는 동안 우클릭이 다시 들어와도 열림 상태 플래그로 중복 열림을 막는다(FR-005).
- **근거**: FR-003. 정지 중에는 정지 이미지를 쓰므로(스펙 Assumptions) 추가 이미지가 필요 없다.

## R4. 캐릭터 설정 화면: 별도 일반 창

- **결정**: "캐릭터 설정"은 프레임이 있는 일반 `BrowserWindow`(포커스 가능, 크기 고정 약
  720×560)다. 같은 렌더러 번들의 두 번째 페이지(`settings.html`)로 빌드하고 전용 preload를 둔다.
  이미 열려 있으면 새로 만들지 않고 앞으로 가져온다. 닫으면 창을 파괴해 메모리를 쓰지 않는다.
- **UI 기술**: 프레임워크 없이 HTML·CSS·TypeScript만 쓴다(화면이 목록·폼·미리보기 정도로 작음).
- **근거**: 오버레이 창은 투명·클릭 통과·포커스 불가라 폼 입력에 맞지 않는다. 설정 창이 열려 있는 동안
  캐릭터가 계속 돌아다니므로 적용 결과를 바로 볼 수 있다(스펙 Edge Cases).

## R5. 이미지 전달: 렌더러가 파일을 읽어 바이트로 메인에 전달

- **결정**: 설정 화면은 `<input type="file" accept="image/png">`로 파일을 받고, 렌더러가 `File`을
  `ArrayBuffer`로 읽어 IPC(`invoke`)로 메인에 보낸다. 경로를 주고받지 않는다. 미리보기는 렌더러가
  `Blob URL`로 처리한다.
- **근거**: 샌드박스된 렌더러가 임의 경로를 메인에 넘기지 않아 안전하고, 네이티브 파일 대화상자 없이
  Playwright `setInputFiles`로 E2E를 자동화할 수 있다.
- **대안**: 메인의 `dialog.showOpenDialog`로 경로 선택(E2E 자동화 불가, 경로 신뢰 문제로 기각).

## R6. 이미지 검증 규칙 (FR-010, SC-005)

검증은 메인이 한다(렌더러 신뢰 안 함). 입력은 "이름, 프레임 수, 걷기 이미지, 정지 이미지"다.

| 항목 | 규칙 | 오류 코드 |
|---|---|---|
| 형식 | PNG만 허용(파일 시그니처로 확인, 확장자·MIME은 신뢰하지 않음) | `not-png` |
| 용량 | 이미지당 5MB 이하 | `too-large` |
| 프레임 수 | 정수 2~32 | `bad-frame-count` |
| 걷기 크기 | 높이 = 프레임 한 변 `S`, 너비 = `S × 프레임 수`, `S`는 64~512px | `bad-walk-size` |
| 정지 크기 | 너비 = 높이 = 걷기와 같은 `S` | `bad-idle-size` |
| 투명 배경 | 두 이미지 모두 알파 값이 255가 아닌 픽셀이 하나 이상 | `not-transparent` |
| 이름 | 앞뒤 공백 제거 후 1~30자, 기존 이름과 중복 불가(대소문자 무시), "기본" 예약 | `bad-name`, `duplicate-name` |
| 손상 | 이미지로 디코딩 불가 | `corrupt-image` |

- **근거**: 기본 캐릭터 규격(200×200 프레임 8장, 표시 크기 100px의 2배)을 허용 범위의 기준으로
  삼았다. 표시 크기는 프레임 크기와 무관하게 100×100 CSS px로 고정하므로 이미지 해상도가 달라도
  캐릭터 크기는 같다.
- **구현**: 규칙은 Electron에 의존하지 않는 순수 함수로 만든다. PNG 헤더(IHDR) 파싱은 순수 TS로,
  "투명 픽셀 존재" 판정만 메인에서 `nativeImage`로 한다(`ImageInspector` 포트로 주입해 테스트에서
  대체한다).

## R7. 저장: 사용자 데이터 폴더의 파일

- **결정**: `app.getPath('userData')/characters/<id>/{walk.png, idle.png}`에 이미지를 복사하고,
  `settings.json`에 목록과 활성 캐릭터를 기록한다. 쓰기는 임시 파일에 쓴 뒤 이름을 바꾸는 방식으로
  원자적으로 한다. 등록 시 앱이 복사하므로 원본을 지워도 영향이 없다(스펙 Edge Cases).
- **손상 대응**: `settings.json`이 깨졌으면 `settings.json.broken-<시각>`으로 보존하고 기본 캐릭터로
  시작한다. 활성 캐릭터의 이미지 파일이 없거나 읽을 수 없으면 활성을 기본으로 되돌리고 설정 화면에
  문제를 표시한다(FR-015).
- **테스트 격리**: 환경 변수 `KAKARU_USER_DATA`가 있으면 그 경로를 사용자 데이터 폴더로 쓴다
  (E2E와 단위 테스트용).
- **스토어 구조**: 파일 입출력은 Electron에 의존하지 않는 `CharacterStore`(루트 경로를 인자로 받음)로
  분리해 임시 폴더에서 단위 테스트한다.

## R8. 활성 캐릭터를 오버레이에 적용 (FR-011, SC-006)

- **결정**: 메인이 활성 캐릭터의 이미지를 `data:` URL로 만들어 모든 오버레이 창에
  `character:appearance` 메시지로 보낸다. 기본 캐릭터는 `walkUrl`·`idleUrl`을 `null`로 보내 렌더러가
  번들에 포함된 기본 이미지를 쓰게 한다. 오버레이 창이 새로 만들어지거나(모니터 추가) 로드가 끝났을 때도
  현재 값을 다시 보낸다.
- **근거**: 별도 프로토콜 등록·경로 검증 없이 기존 CSP(`img-src 'self' data:`)로 동작한다. 적용은
  드물게 일어나는 사건이라 base64 전송 비용이 문제되지 않는다.
- **오버레이 렌더링**: 걷기 이미지의 프레임 수를 CSS 변수로 받아 `steps(N)`과 이동 거리, 한 바퀴
  시간(`max(560ms, 프레임 수 × 70ms)`)을 계산한다. 기본 캐릭터(8프레임)와 샘플 캐릭터(4프레임)는 모두 한 바퀴 0.56초다.
  위치·방향·이동 상태는 바뀌지 않는다(FR-011).
- **적용 중 오류**: 이미지 로드 실패(`onerror`) 시 렌더러가 기본 이미지로 되돌린다(FR-015 보강).

## R9. 기본 캐릭터

- **결정**: 001에서 만든 `walk.png`(8프레임), `idle.png`(폴리곤 고양이)를 기본 캐릭터로 취급한다. 코드 번들에
  포함되며 사용자 데이터 폴더에는 복사하지 않는다. 목록에는 항상 맨 위에 "기본"으로 나타나고
  삭제할 수 없다(FR-014).

## R9-2. 샘플 캐릭터 "빨간 모자" (처음 실행 때 등록)

- **결정**: `specs/bmm.png` 기반으로 만든 이미지(걷기 4프레임, 정지 1장)를 `resources/characters/bmm/`에
  두고, 앱을 처음 실행할 때 등록된 캐릭터("빨간 모자")로 한 번만 넣는다. 활성 캐릭터는 바꾸지
  않으므로 사용자가 선택하기 전에는 기본 캐릭터(폴리곤 고양이)를 쓴다. 이름은 이미지 원본에 이름이
  없어 외형(빨간 두건)을 따라 붙였다.
- **한 번만**: `settings.json`의 `seeded`에 키(`bmm`)를 기록해 두고, 삭제해도 다시 넣지 않는다.
  이미지 파일이 없으면 건너뛴다.
- **근거**: 기본 캐릭터는 코드에 내장된 읽기 전용이라 삭제할 수 없지만, 샘플은 사용자가 지우고
  싶을 수 있다. 일반 등록 캐릭터와 같은 저장 경로·규칙을 쓰므로 별도 코드가 필요 없다.
- **대안**: 기본 캐릭터를 둘로 늘림(읽기 전용 항목이 늘고 "기본으로 되돌리기" 대상이 모호해져 기각).

## R10. 성능 영향 (헌장 원칙 III)

- 네이티브 메뉴와 설정 창은 필요할 때만 생성되므로 유휴 상태의 CPU·메모리에 영향이 없다.
- 001의 SC-006(CPU 10% 이하)을 유지한다. 설정 창이 열려 있는 동안은 측정 대상에서 제외한다.
- 걷기 애니메이션은 프레임 수가 달라져도 compositor가 처리하므로 프레임마다 JS가 돌지 않는다.

## R11. 범위 밖 메모

- 앱을 종료할 메뉴 항목이 없다(Dock·메뉴 막대에도 앱이 보이지 않는다). 스펙 범위에 없으므로 만들지
  않았지만 곧 필요하다. 후속 기능 후보로 남긴다.
